Missing Screens

Design gaps

Screens either not designed at all, or backend features that have no corresponding UI surface. These will block frontend implementation.

Public unauthenticated tracking page
Critical Design missing

PRD Q2 explicitly states: "No customer login required for tracking (tracking code + phone verification)." The backend exposes GET /v1/shipments/{code}?phone= as a public route with no JWT requirement. However no design screen exists for this surface — there is no /track/{code} or public lookup page in any of the 15 design sections. Section 10 (Customer Portal) requires a login throughout.

Backend GET /v1/shipments/{code}?phone= — implemented, no JWT, phone verification against customer record
Design needed A standalone page (no sidebar, no auth) — tracking code entry + phone verify → read-only tracking stepper. Tenant-branded via subdomain. Mobile-first.
Scope New screen. Can reuse the tracking stepper component from Section 10.1.
Notification delivery log — no backend persistence or API
Critical Backend missing

Section 14.11 is a fully designed screen — notification log with channel filters, delivery status, retry button, and a gateway-response detail modal. The backend notification handlers (sms_handler, whatsapp_handler, email_handler) process SQS messages but only emit CloudWatch logs. There is no notification_log DB table, no GET /v1/notifications/log endpoint, and critically no retry endpoint. The WhatsApp delivery status webhook (_handle_whatsapp_delivery_status) parses status callbacks from Meta but only logs them — it never writes to a DB.

Design has Log list with channel/status/customer filters, detail modal with gateway response body, "Retry" action button
Backend has CloudWatch logs only. No table. No API. No retry capability.
Needed Migration for notification_log table. GET /v1/notifications/log endpoint in notification or tenant_management handler. Retry endpoint. Wire WhatsApp delivery callback to persist status.
Platform Admin impersonation — designed but no backend
Critical Backend missing

PRD Q12 defines read-only Platform Admin impersonation of Tenant Admins with full audit controls (logged start/end, read-only session, 30-min auto-expiry). The Section 2.4 Tenant Detail design shows a "View as Tenant Admin" action button. There is no implementation in any handler — no POST /v1/platform/tenants/{id}/impersonate, no session token mechanism, and no impersonation audit trail in the codebase.

PRD ref Q12: read-only, audit-logged, 30-min expiry, platform_audit_log entry with start/end timestamps
Design has "View as Tenant Admin" button in Section 2.4 tenant detail action bar
Backend has Nothing. No endpoint, no impersonation token, no audit hook.
Options Short-lived JWT with impersonated_by claim injected server-side, OR link to Cognito console (simpler but loses audit trail)
PDF export — designed, zero backend implementation
Critical Backend missing

Section 14.12 shows production-quality A4 print layouts (794×1123px) for both packing lists and release notes, including a QR code on the release note and an APPROVED stamp on the packing list. The backend services/excel/ has export_packing_list.py, export_manifest.py, and export_billing.py — all Excel. There is no PDF generation service, no QR code library, and no PDF Lambda route anywhere in the codebase.

Design has A4 packing list with APPROVED stamp; A4 release note with QR code + signature block (Section 14.12)
Backend has Excel only (openpyxl). No weasyprint, reportlab, or equivalent in requirements.txt.
Needed PDF Lambda route (GET /v1/packing-lists/{id}/pdf, GET /v1/release-notes/{id}/pdf), QR code generation (qrcode lib), S3 presigned download URL response
Outbound webhook configuration screen
High Design missing

The backend fully implements outbound webhooks to tenant ERP/WMS systems — shared/webhook.py handles HMAC-SHA256 signing, and webhook_config (URL, secret, enabled flag, events list) is stored in tenant_config. Tenant Admin config screens (Section 4) cover: Company Settings, Dollar Rate, CBM Rate, Charge Types, Notification Templates — but there is no webhook configuration screen. Tenants with integrations have no UI to set this up.

Backend has webhook_config in DEFAULT_CONFIGS, HMAC signing in shared/webhook.py, fires on container.status_updated
Design needed New nav item under Section 4 config: Webhook — URL input, secret generation/reveal toggle, enabled toggle, events checklist, test-fire button
Document download — upload exists, no download URL in API
High Backend incomplete

Section 5.3 Container Detail → Documents tab shows a download button per uploaded document. The backend exposes POST /v1/containers/{id}/documents/presigned-url for S3 upload and GET /v1/containers/{id}/documents for listing. But the list endpoint returns document metadata — it doesn't return a signed download URL. There is no GET /v1/containers/{id}/documents/{doc-id}/download route, and the frontend cannot access S3 directly (private bucket, tenant-scoped prefix).

Missing GET /v1/containers/{id}/documents/{doc-id}/download → returns short-lived S3 GetObject presigned URL
Touches services/tracking/handler.py, services/tracking/service.py
Platform settings — notification provider credentials UI vs env vars
High Design/backend mismatch

Section 2.5 Platform Settings shows a detailed "Notification Providers" panel — SMS gateway config (API key, from number), WhatsApp Business API config (phone number ID, access token), and a test-send button per channel. The backend stores all of these as Lambda environment variables set at deploy-time in Terraform. There is no platform_settings table API (Task 21 Part 4 defines it but the acceptance criteria tick is for a DB-backed API, not env vars). As designed, these would need to be runtime-configurable via API.

Design expects Runtime-editable via UI → stored in platform_settings table or Secrets Manager
Backend reality Env vars set at deploy time: AFRICA_TALKING_API_KEY, WHATSAPP_ACCESS_TOKEN, etc. No API to update them.
Decision needed Either (a) implement platform_settings API + Secrets Manager integration, or (b) scope down the design to "read-only status view + link to AWS Console"
Locale / language preference — no UI to set it
Medium Design missing

Migration 026 adds tenant_user.locale VARCHAR(10) DEFAULT 'en' for EN/ZH notification routing. China Office Staff would typically set this to zh. No design screen surfaces this preference — not in Section 3 (Staff User Profile), not in account settings of any portal. The locale silently defaults to English for all users.

Needed Language selector (EN / 中文) in staff profile/account settings — Section 3.4 Staff User Profile edit panel

API ↔ Design Mismatches

Alignment gaps

Places where a backend contract, constraint, or response shape doesn't match what the design assumes — these will cause bugs or unexpected behavior during integration.

Design font stack contradicts design system spec
High Inconsistency

The Section 0 design system foundation document specifies Inter as the font family. Every one of the 15 HTML design screens uses Manrope + Kumbh Sans + JetBrains Mono. This isn't a bug, but it means the design system spec and the implemented screens are out of sync. Any developer referencing Section 0 as the source of truth will build with the wrong font, and the design screens can't be used as a reference for the component library without reconciliation.

Spec says Inter (Google Fonts), fallback system-ui
Screens use Manrope (headings/display), Kumbh Sans (body), JetBrains Mono (code/IDs)
Action Update Section 0 spec to reflect Manrope/Kumbh Sans, OR update all screens to Inter. The screens are the stronger reference; update the spec.
Container number format constraint not surfaced in forms
High UX gap

The backend enforces pattern=r"^[A-Z]{4}\d{7}$" on container numbers (e.g. MSCU1234567) per 00_CROSS_CUTTING_STANDARDS.md §2.1. Section 5.2 Create Container shows a free-text input with no format hint, no validation message, and no monospace rendering. Users unfamiliar with ISO 6346 container codes will fail validation with a cryptic 422 error.

Backend Pydantic rejects non-matching values with VALIDATION_ERROR (422)
Design fix Add format hint ("4 letters + 7 digits, e.g. MSCU1234567"), monospace input font, inline pattern validation on blur
Bulk approve/reject — no partial failure state designed
High Missing state

The bulk approve/reject endpoints (POST /v1/packing-lists/bulk-approve) return a partial success response: {"succeeded": [...], "failed": [{"id": "...", "reason": "..."}]}. The design in Section 5.6 shows a bulk reject modal and a confirm action, but there is no designed state for the result where some items fail (e.g. self-approval blocked, wrong status). A user approving 20 packing lists and getting silent partial failure is a significant UX problem.

API response {"succeeded": [ids...], "failed": [{"id": "...", "reason": "..."}]}
Design needed Post-bulk-action result state: "18 approved, 2 failed" with failed items listed with reasons. Inline in the table or a result modal.
Weight reconciliation output not surfaced in manifest design
Medium Design gap

The manifest verify endpoint (PATCH /v1/manifests/{id}/verify) returns a weight_discrepancies array flagging items where actual vs dispatch weight diverges by more than 5% or 0.1kg. Section 6.3 Manifest Detail shows a verify modal with a discrepancy form for missing/damaged cartons — but does not show the weight discrepancy report. Staff who verify manifests won't see automated weight flags.

API returns weight_discrepancies: [{item_id, carton_tag, dispatch_kg, actual_kg, delta_kg, delta_pct}]
Design fix Add a "Weight Discrepancies" section in the manifest detail / verify result, showing flagged items in an amber alert card
Refund threshold — no visual explanation of escalation rule
Medium UX gap

The backend enforces a configurable refund approval threshold: Nigeria Office Staff are hard-blocked from approving refunds above staff_limit (default $50 USD). Section 8.6 Refund Detail shows a "5-step approval stepper" but doesn't explain why certain approvals escalate or show the current threshold. A staff member trying to approve a $75 refund will receive an opaque APPROVAL_THRESHOLD_EXCEEDED 403 error with no explanation in the UI.

Backend 403 APPROVAL_THRESHOLD_EXCEEDED when Nigeria Staff tries to approve above staff_limit × dollar_rate NGN
Design fix Show threshold amount in the approve modal ("Staff can approve up to ₦82,500 / $50. This refund requires Tenant Admin approval.") and disable the approve button for out-of-scope staff

Role & Access Gaps

Role mismatches

Cases where the design attributes actions to the wrong role, or where a role's permissions in the backend don't match what the design implies they can do.

China Office cannot update container status in the design
High Wrong role attribution

Section 5.3 Container Detail describes the status update dropdown as "Nigeria Office only." The backend (PATCH /v1/containers/{id}/status) explicitly allows china_office_staff to update China-side stages: received_at_china_warehouse, packed_in_container, in_transit. Nigeria Office handles the arrival-onwards stages. The design incorrectly locks China Office out of status updates in their own portal — the "Update Status" control should be visible to both roles, filtered to their permitted transitions.

Backend China: received_at_china_warehouse → packed_in_container → in_transit. Nigeria: arrived_nigeria → customs_clearance → cleared → ready_for_pickup → completed
Fix Show status update control in Section 5.3 (China portal) with China-permitted transitions only. Remove "Nigeria Office only" label.
NDPR mentioned in customer privacy tab — not implemented in backend
Medium Compliance gap

Section 10.7 Customer Account → Privacy tab references both GDPR and NDPR (Nigeria Data Protection Regulation). The backend and PRD implement GDPR Art. 17 (erasure) and Art. 20 (portability). NDPR has its own consent and breach notification obligations distinct from GDPR. The backend currently has no NDPR-specific handling, and the consent_given_at / notification_consent fields are GDPR-aligned. If the platform processes Nigerian citizens' data, NDPR compliance should be explicitly scoped.

Action Either (a) confirm NDPR is sufficiently covered by the GDPR implementation for v1, and update design copy to reflect this, or (b) scope a separate NDPR compliance task
Tenant offboarded (410) — no error screen designed
Medium Missing state

When a tenant is offboarded, all their users' JWTs hit a 410 TENANT_OFFBOARDED error on every request after the Redis cache is invalidated. The design has no screen for this state — no "Your account has been closed" page, no data export prompt, no graceful offboarding landing. Users will see a raw error or a blank screen.

Similar to Section 1.1 Login has "tenant suspended" error state — that pattern can extend to a full offboarded page
Needed A full-page offboarded state (no sidebar): "This account has been closed. Contact ShipX support if you believe this is an error." + support email

Scheduled Jobs Without UI

Background processes

The backend has 7 scheduled jobs running automatically. Several have observable side-effects that users will encounter without any designed UI to explain or interact with them.

Storage fee accrual — no grace period countdown in design
High Missing UI state

scheduled/storage_fee.py accrues daily storage fees after a 14-day grace period (per PRD Q7: ₦500/day/carton configurable). Reminders fire at day 7 and day 13. The design doesn't show: (1) a "grace period expires in X days" countdown on the release note or billing detail, (2) a storage fee accrual warning on the customer portal, or (3) the storage fee line items building up in the billing detail view after the grace period expires.

Affects Section 7.2 Billing Detail (storage fees tab exists but no countdown), Section 10.2 Shipment Detail, Section 9.2 Release Note Detail
Needed Amber banner on billing/release note: "Storage fees begin accruing in X days (₦500/day/carton)". Red banner after grace period: "Storage fees are accruing — ₦X,XXX accumulated so far."
CBM dispute auto-escalation — no visual distinction in design
Medium Missing state

scheduled/dispute_escalation.py auto-escalates CBM disputes to Tenant Admin if China Office doesn't respond within 5 business days (PRD Q1: 7-day SLA). The design for Section 7 (Billing Disputes) doesn't distinguish between a manually-escalated dispute and a system-escalated one, and doesn't show any SLA countdown timer on the dispute detail.

Needed Dispute detail: SLA countdown chip ("Escalates in 2 days"), system-escalated badge (distinct from manual), escalation event in the dispute audit timeline
Release note expiry — no expired state in design
Medium Missing state

scheduled/release_expiry.py expires release notes after a configurable period. Section 9.1 Release Notes List shows an "Expired" status badge, but Section 9.2 Release Note Detail doesn't show what an expired release note looks like — no warning, no re-issue CTA, no explanation for the warehouse attendant of what to do when they scan an expired release note.

Needed Release note detail: "Expired" state variant — red header banner, "Request New Release Note" CTA (if outstanding balance still exists), warehouse view should show expired status prominently
SLA check job — monitoring output not exposed anywhere
Low Observability

scheduled/sla_check.py monitors SLA compliance. Its output goes to CloudWatch only. The Tenant Admin dashboard (Section 3.1) and the Nigeria Office Dashboard (Section 6.1) would both benefit from an SLA health indicator — e.g. "2 disputes at risk of SLA breach" — but neither shows this.

Nice to have SLA at-risk count on the Nigeria Office urgent actions panel (Section 6.1) and the Tenant Admin reports page (Section 14.10)
Usage aggregation feeds reports — verify API wired to Section 14.10
Low Verify

scheduled/usage_aggregation.py aggregates metered usage. Section 14.10 Tenant Reports shows business KPIs (containers, revenue, claims, CBM/billing table). The GET /v1/tenant/reports endpoint is marked complete in the docs but wasn't confirmed in a handler read. Verify this endpoint exists in services/tenant_management/handler.py before the frontend team attempts to integrate Section 14.10.

Action Grep tenant_management/handler.py for reports route. If missing, implement per Task 21 Part 5 spec.
