Critical — the read-only impersonation guard is never invoked

Security
⚠ Impersonation is not actually read-only at runtime
The guard exists and the docs mark it done — but no write handler calls it. A "read-only" impersonation session can currently mutate tenant data.
Mutating handlers don't call assert_not_read_only()
CriticalBackend

The plumbing is all there: the authorizer injects read_only=true + impersonated_by, shared/auth.py populates TenantContext.read_only, and assert_not_read_only(ctx, method) is defined to raise IMPERSONATION_READ_ONLY on any non-GET. But a full-codebase search shows the guard has zero call sites — it is never imported or called by tracking, billing, claims, refunds, packing_list, manifest, payment_release, or the tenant_management write routes. So despite the read-only contract (PRD Q12), an impersonation token can POST/PATCH/DELETE freely.

Definedshared/auth.py:95 — assert_not_read_only(ctx, method)
Called bynothing (only referenced in docs, which mark it [x] complete — the checkbox is wrong)
FixCall assert_not_read_only(ctx, method) at the top of every write dispatch (or centralise it in a shared router/decorator so no handler can forget). Add a test asserting an impersonation token gets 403 on a POST.
ImpactUntil wired, the headline safety property of impersonation is unenforced — a support session could alter billing, approve refunds, change config.

Backend seams — built but not reachable

Half-wired

Features whose storage + downstream consumers exist, but with no write path — so the matching UI can't actually persist anything.

Webhook config has no save endpoint
HighBackend

webhook_config is seeded in DEFAULT_CONFIGS and the outbound webhook fires from tracking via fire_tenant_webhook. But UpdateTenantConfigRequest only accepts branding and notification_preferences, and update_tenant_config() writes only those two keys. There is no way to set the URL, secret, enabled flag, or events list through the API — so the new Webhook config screen (gap-fix B2) has nothing to call.

Evidencetenant_management/models.py:83 (request model) + service.py:453 (only branding/notification_preferences persisted)
FixAdd webhook_config to UpdateTenantConfigRequest (validate URL, events enum) and persist it in update_tenant_config(); add a test-fire endpoint to back the screen's "Send test event" button.
Staff locale (EN/ZH) cannot be set
HighBackend

Migration 026 added tenant_user.locale and the notification stack fully honours it — enqueue_notifications passes locale through SQS and the handlers select ZH templates when locale == 'zh'. But update_user() whitelists only full_name and role, so locale can never be written. The EN/ZH feature is dead on the write side: every user stays at the 'en' default, and the Locale Preference screen (gap-fix A6) has no field to PATCH.

Evidencetenant_management/handler.py:448 — updates = {k:v ... if k in ("full_name","role")}
Also verifythat the notification callers (e.g. tracking's container_arrived) look up the recipient's locale and pass it into enqueue_notifications — otherwise it defaults to 'en' even once settable.
FixAdd locale to the permitted update_user fields (validate against EN/ZH) and to the customer profile if customers can choose language.

Frontend seams

UI gaps
No read-only banner inside an impersonated session
MediumFrontend

The platform screen has a "View as Tenant Admin" button (platform-screens.jsx:526) and the backend returns impersonated_by / read_only / session_id in context. But once inside the tenant portal there's no persistent impersonation banner, no 30-minute session countdown, no "Exit impersonation" control, and mutating actions aren't visibly disabled. A platform admin can't tell they're impersonating, and (combined with the critical guard gap) nothing stops them clicking a write action.

NeededA sticky top banner ("Viewing as Tenant Admin · read-only · ends in 28:14 · Exit"), disabled state on all primary/destructive buttons, and a clean exit that calls DELETE /v1/platform/impersonation/{session_id}.
NoteThe app needs a way to read the current impersonation state — decode the token claims client-side, or add a small /v1/session echo endpoint.
11 gap-fix screens remain only in the Section 16 showcase
LowIntegration

The notification log was grafted into its home (Section 14.11). The other gap-fix screens — public tracking, China status update, container-number hint, bulk partial result, refund threshold modal, webhook config, storage-fee banners, weight discrepancy, dispute SLA, expired release note, locale preference — still live only in gapfix/ and the Section 16 canvas. That's fine as a review showcase, but they aren't wired into Sections 4–9 where users actually reach them.

DecisionEither keep Section 16 as the canonical gap-fix showcase, or graft each screen into its home section (e.g. status-update into Section 5 China, webhook tab into Section 4 config, public tracking as its own route shell).
