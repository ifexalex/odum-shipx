# ADR-008: A one-time pickup code on each release note

**Status:** Accepted (2026-11-16, owner decision on audit finding UX-09: "one-time pickup code", not a QR code).
**Related:** `shared/pickup_code.py`, `services/payment_release/service.py`, migration 065,
`13_api_payment_release.md`, `docs/runbook.md`.

## Context

An in-person pickup needed only a typed collector name. Anyone who knew a release-note reference, which is printed on
the note and sent in a message, could collect the goods. Delegates give ID details; the customer in person gave nothing.

## Decision

* **Each release note gets a six digit code**, issued when the note is created (generate, split, reissue) and sent to
  the customer by SMS and email (`pickup_code_issued`). Whoever collects, the customer or a delegate, gives it to the
  warehouse attendant, and `record_pickup` refuses the pickup without it. A delegate still gives ID details as well.
* **Only a keyed hash is stored**: HMAC-SHA256 under `PICKUP_CODE_PEPPER`, bound to the note's id. Six digits is a
  million possibilities, so an unkeyed hash could be reversed by anyone who can read the table; the pepper is not in
  the database. The plaintext exists in the message to the customer and nowhere else: not in the API, the audit log,
  application logs, or `notification_log` (the stored message body and template data are masked, and a failed code
  message cannot be retried, because there is nothing to resend).
* **Five wrong codes lock the note** (`pickup_code_failed_attempts`, incremented atomically in SQL). A locked note
  refuses even the right code until staff send a new one (`POST /v1/release-notes/{id}/pickup-code`: tenant admin and
  Nigeria staff), which retires the old code and resets the count. Staff are told in app when a note locks. An empty
  code field is asked for and does not count as a guess.
* **Nobody at the company sees the code.** Staff can send a new one; the response says where it went, never what it is.
* **A note without a code needs none.** That covers notes issued before migration 065, a customer with no phone or
  email, and a code that could not be put on any queue (the hash is cleared again). Requiring a code that nobody
  received would only stop the collection, and staff can issue one later.
* **Fails closed where it matters.** If a note carries a code but the pepper is missing, the pickup is refused (503),
  not waved through.

## Consequences

* The pepper is generated by Terraform (`random_password`) and injected into the Lambdas and the container app.
  **Rotating it makes every outstanding code unverifiable**; each affected active note then needs a new code.
* **Outside production the notification guard suppresses messages** to anyone not on `NOTIFICATION_ALLOWLIST`, so in a
  dev or staging environment with the pepper set, a test customer must be on the allowlist to receive a code, or the
  pickup cannot be completed for a note that has one. Local dev has no pepper by default, so no codes are issued.
* The code travels by SMS and email, which are only as private as the customer's phone and inbox. That is the level
  of assurance chosen; a QR code on the printed note was the alternative and was not wanted.
* The count is per note, not per attendant or address. Someone at the counter can lock a note with five wrong tries;
  that is a denial of one pickup, visible to staff, and fixed by sending a new code.
