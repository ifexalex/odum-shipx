# Frontend Master Plan

## Purpose

This folder is the frontend equivalent of `../00_MASTER_PLAN.md`. The backend (services 06–21) is complete. The visual design is complete and lives in `Shipx_frontend_design/` at the repo root. **No frontend application code exists yet.** These docs are the build plan an engineer (or another agent) follows to implement it from scratch, iteratively, service by service.

Read this file first, then follow the Task File Index in build order. Each doc has the same shape as the backend task docs: Objective → Depends On → Deliverables → Acceptance Criteria (`- [ ]`, check off as built).

## Source of Truth Hierarchy

When in doubt, resolution order is:

1. **Backend code** (`services/*/handler.py`, `models.py`) — the actual API contract. Route inventories in these docs were generated by reading the handlers directly; if backend code has moved on, re-derive from code, not from these docs.
2. **`Shipx_frontend_design/`** — the approved visual design. Screens are real JSX (not static images) at `Shipx_frontend_design/screens/**/*.jsx`, using a shared component library (`screens/shared/components.jsx`, `screens/shared/app-shell.jsx`) and a design-token object `T`. These are reference mockups, not production code — they're untyped, have no real data fetching, and use inline styles instead of a build system. Port the visual language and component contracts; don't import the files directly.
3. **These frontend docs** — synthesis of the two above, plus the architectural decisions needed to turn mockups into a real app.

## Architecture Decision

**React 18 + TypeScript + Vite, deployed as a static SPA to S3 + CloudFront.** No SSR.

Why: the entire app is behind a Cognito login (no public SEO surface except the one public tracking page, which doesn't need indexing); pairs with the existing AWS-native backend (API Gateway + Lambda + Cognito) with zero new compute; CloudFront scales globally for free at this traffic tier and serves both China- and Nigeria-side users from edge. Full infra plan: [13_deployment_and_cicd.md](13_deployment_and_cicd.md).

**Multi-tenant routing:** the design mockups use two domain patterns — `shipx.co/...` for the app shell (platform admin, tenant admin, staff, customer self-service) and `{tenant}.shipx.co/...` for tenant-branded/white-labeled customer-facing surfaces (public tracking, impersonated portal view). Treat the subdomain as **cosmetic only** — it selects which `branding_config` to render pre-auth (logo, color, company name on the login screen). It must never be trusted as the tenant_id. Post-login, `tenant_id` always comes from the JWT (`custom:tenant_id` claim) returned by Cognito, per [04_auth_and_session.md](04_auth_and_session.md). This preserves the backend's 4-layer tenant isolation (CLAUDE.md) — the frontend is not a trust boundary for tenant resolution.

## Conventions Carried Over From Backend Docs

These CLAUDE.md rules apply to frontend work too:

- **Doc-First Rule**: when you build a page or change an API integration, check off the relevant `- [ ]` in that doc's Acceptance Criteria in the same change.
- **No secrets in code**: Cognito client ID/pool ID and API base URL are build-time env vars (`VITE_*`), never hardcoded. No API keys belong in frontend code — anything secret (webhook signing secret, etc.) is fetched/rotated server-side only.
- **No PII in logs**: browser console/error-reporting (Sentry or equivalent) must scrub email, phone, name, ID numbers before reporting, same as backend CloudWatch rule.
- **Tenant isolation is a backend property, not a frontend one**: the frontend never filters tenant data client-side for security — it relies entirely on the API returning only tenant-scoped data. Client-side role checks (Phase 2 routing) are UX convenience (hide a button), not a security boundary; the API enforces the real boundary.
